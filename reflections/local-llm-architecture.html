Sovereign AI Without Cloud Leakage

How I use frontier cloud models for complex reasoning while confidential data — client records, financials, PII — never leaves the machine.

The question every privacy-conscious practitioner faces with AI is a false dilemma: either accept cloud models and send sensitive data over the wire, or refuse them and give up frontier reasoning capability. My working answer over the past months has been a split-plane architecture — cloud and local LLMs each doing what they are best at, with a hard privacy boundary between them.

The local plane

All confidential work happens on-device. On an Apple Silicon host with 256 GB of unified memory, open-weight models such as Qwen 27B and DeepSeek-V4 run locally with zero latency, complete data residency, and zero marginal token cost. Behind a LiteLLM gateway I route different tasks to different local models — a fast coding model, a deep-reasoning model, an embeddings server — and the whole stack (gateway, Neo4j knowledge graph, Qdrant vector store, Redis) runs in containers with every port bound to loopback only. There are no cloud API keys anywhere in the configuration: egress is blocked structurally, not by policy.

The four mechanisms of the air-gap

Deterministic hooks, not prompts. Most AI privacy setups rely on prompt instructions ("please do not leak secrets"). LLMs are probabilistic and inevitably fail. Instead, an OS-level hook intercepts file reads and shell commands: any attempt to touch files matching confidential patterns (PII, financials, credentials) is hard-blocked before anything reaches the network.

On-device tool delegation. When a cloud agent encounters a task requiring sensitive records, it does not inspect the file. It issues a structured call to an on-device Model Context Protocol (MCP) server. The file path stays local; raw bytes never leave the host.

Local compute for the sensitive step. The MCP server routes processing directly to the on-device models, which read the raw data and do the analysis where it can't leak.

Format-preserving surrogates. The local model strips names, account numbers, and credentials, replacing them with structured surrogate tokens (<PERSON_1>, <ACCOUNT_A>) or mathematical aggregates. The cloud model then works safely on the sanitized structure — it gets the shape of the problem without any of the sensitive content.

Where it applies

Financial & ledger auditing. Reconcile transactions, detect discrepancies, and analyze multi-year balance sheets without uploading private financial statements to third-party model providers.

Client records & PII. Process intake forms, donor lists, or customer datasets. Sensitive identifiers are replaced with consistent surrogate tokens on-device, enabling cloud agents to design databases and user flows safely.

High-volume code work. Offload file diffs, test generation, and schema verification to local compute at $0 marginal cost per token — which is what makes overnight autonomous runs economically sane.

Why this split, and not "all local" or "all cloud"

All-local means accepting weaker reasoning on the hardest problems; all-cloud means accepting that a prompt-level privacy promise is only as strong as the model's compliance. The split plane keeps both options: frontier capability for planning and code generation, sovereign compute for anything confidential — with the boundary enforced by deterministic tooling rather than trust. As open-weight models keep closing the gap, the local side of this trade gets stronger every quarter, but the architecture doesn't depend on that trend; it works whichever side is winning.
